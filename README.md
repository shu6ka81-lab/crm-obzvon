# CRM обзвона — «Офисная Служба»

Рабочий инструмент обзвона клиентской базы. Первая версия закрывает одну задачу:
позвонить по списку, зафиксировать результат и увидеть воронку.

Спецификация и обоснование решений — `../11_CRM_v1_спецификация.md`.

---

## Запуск

```bash
npm install
npm run db:seed          # миграции + пользователи + импорт выгрузки + кампании
npm run dev              # http://localhost:3000
```

`db:seed` по умолчанию берёт выгрузку из `C:\Users\ден\Downloads\Kontragenty_Aktivnost_26.xlsx`.
Другой файл — первым аргументом: `npm run db:seed "путь\к\файлу.xlsx"`.

## Скрипты

| Команда | Что делает |
|---|---|
| `npm run dev` | Дев-сервер |
| `npm run build` | Продакшен-сборка |
| `npm run db:generate` | Сгенерировать миграцию после правки схемы |
| `npm run db:seed` | Развернуть базу с нуля |
| `npm run db:check` | Прогнать парсер выгрузки 1С и показать сводку, без записи в базу |
| `npm run db:reset-activity` | Стереть касания, квалификацию и задачи, сбросить очереди. Клиентов не трогает |

## База данных

Одна схема, две среды:

- **разработка** — PGlite: настоящий Postgres внутри процесса, ставить ничего не нужно. Данные в `./.pglite`.
- **продакшен** — обычный Postgres, адрес в `DATABASE_URL`.

SQL и миграции одинаковые, поэтому расхождений между средами нет.

> **Важно:** PGlite работает только из одного процесса. Нельзя одновременно
> держать запущенным дев-сервер и выполнять скрипты вроде `db:seed`.
> Сначала остановите сервер. На продакшене этого ограничения нет.

## Обмен с 1С

У клиента **1С 7.7** (предположительно — подтвердить через «Помощь → О программе»).
API там нет и быть не может, поэтому обмен только файлами.

### Импорт

Берётся отчёт **«Активность контрагентов»** — тот самый файл, который 1С уже умеет
выгружать. Дополнительно настраивать ничего не нужно.

Ключ связи — **код контрагента из 1С** (`clients.code_1c`). Он стабилен и не меняется.

Повторная загрузка того же отчёта обновит данные из 1С и **не затрёт** то, что
заполнили мы: квалификация, касания и задачи лежат в отдельных таблицах.

### Экспорт (ещё не реализован)

CSV в кодировке Windows-1251 в папку `H:\1C_Dir\CRM_Выгрузка\` — там, где у клиента
уже работает файловый обмен с сайтами. Их разработчику останется написать одну
обработку загрузки.

## Модель данных

Ключевые решения:

- **`qualifications` — append-only.** Каждое изменение пишется новой строкой, актуальная
  версия — последняя по времени. Так видно, что про клиента знали полгода назад.
- **`campaign_clients`** — списки обзвона живут параллельно и считаются раздельно.
  Кампания знает порядок очереди и состояние каждой карточки.
- **`preset_budget`** в `campaign_clients` — для списков, собранных из КУДиР, где
  обороты известны до звонка. Менеджер только подтверждает цифру.
- **`touches`** — история касаний, а не последнее значение.
- Клиенты не удаляются физически, только `deleted_at`.

## Логика очереди

После сохранения звонка карточка двигается так:

| Результат | Что происходит |
|---|---|
| Дозвонился, Отказ, Номер не тот | карточка закрыта в этой кампании |
| Просили перезвонить | отложена, создаётся задача с датой |
| Не взяли, Занято | уходит в конец очереди, вернёмся позже |
